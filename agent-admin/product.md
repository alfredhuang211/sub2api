# Agent Admin 产品说明

## 1. 项目定位

`agent-admin` 是面向代理经销商的独立管理平台。它后续作为独立项目开发、构建、部署和升级，不再要求修改 `sub2api` 原项目代码。

新的产品边界：

- `sub2api` 继续负责原系统能力：用户账号、登录认证、原推荐系统、原订单、套餐和用量数据。
- `agent-admin` 自己负责代理业务能力：代理身份、代理层级、客户归属、分成比例、佣金生成、结算、审计日志和代理端/管理员端 API。
- 两个项目部署在同一服务器或同一内网环境中。
- 两个项目共用同一个数据库。
- `agent-admin` 可以读取 `sub2api` 既有表，但不修改 `sub2api` 代码，不给原表新增字段。
- `agent-admin` 自有表由 `agent-admin` 自己迁移和维护。

## 2. 阶段目标

### P0：独立 Agent Admin MVP

- 独立 `agent-admin-web` 前端。
- 独立 `agent-admin-api` 后端。
- 复用 `sub2api` 登录能力和账号体系。
- `agent-admin-api` 连接同一个数据库，读取原 `users`、推荐、订单、套餐等表。
- `agent-admin-api` 自己创建和维护 `agent_*` 业务表。
- 原系统管理员可以登录 `agent-admin` 并管理代理体系。
- 已被指定为代理商的原系统用户可以登录 `agent-admin`。
- 管理员可以从原系统用户中指定代理商。
- 管理员可以设置代理等级、上级代理、分成比例。
- 管理员可以手动设置客户归属代理。
- 代理商可以查看自己的客户、佣金、结算、上级代理和下级汇总。
- 代理商可以把直接归属于自己的可发展用户指定为下级代理商。
- 代理商可以在权限范围内设置下级代理分成比例。

### P1：结算与运营增强

- 自动生成自然月结算记录。
- 管理员标记结算已支付。
- 完善冲正、退款抵扣、结算账户和运营报表。
- 补充订单、套餐周期、客户详情的只读展示。

### P2：代理经营能力扩展

- 代理结算申请。
- 代理员工子账号。
- 代理专属套餐和价格策略。
- 客户分层运营和报表导出。
- 自动打款或第三方打款集成。

## 3. 系统边界

### sub2api 负责

- 原用户注册、登录、密码、OAuth、JWT 签发。
- 原系统管理员角色。
- 原推荐码和推荐关系。
- 原支付订单。
- 原订阅套餐。
- 原用量和套餐消耗。
- 原后台、原用户端和原 API 网关能力。

### agent-admin 负责

- 代理身份和代理等级。
- 代理上下级关系。
- 代理客户归属关系。
- 代理分成比例。
- 周期佣金生成。
- 结算记录。
- 代理业务审计。
- 代理端 API。
- 代理管理员 API。
- 自有表迁移。
- 自有调度任务。

### 不做的事

- 不修改 `sub2api` 代码。
- 不把 agent-admin 业务 API 注册到 `sub2api` 后端。
- 不让 `agent-admin-web` 直接连接数据库。
- 不直接改变原推荐系统逻辑。
- 不默认把管理员手动归属写回原推荐系统。

## 4. 账号体系与认证

账号体系与原系统保持一致：

- 继续使用 `sub2api.users` 作为唯一用户账号来源。
- 管理员和代理商使用与原系统一致的账号密码。
- 代理身份是原系统用户账号上的业务身份扩展。
- `agent-admin` 不创建独立账号体系。

认证方式已确认如下：

### 已确认方案：agent-admin-api 代理登录 + 本地验签

- 用户在 `agent-admin-web` 登录时调用 `agent-admin-api` 登录代理接口。
- `agent-admin-api` 将登录请求转发到 `sub2api` 登录接口。
- 登录成功后获得 `sub2api` JWT。
- 前端请求 `agent-admin-api` 时携带该 JWT。
- `agent-admin-api` 配置与 `sub2api` 一致的 JWT 校验参数，按 `sub2api` 当前规则本地验签。
- `agent-admin-api` 本地验签后读取共享数据库中的 `users` 和 `agent_profiles` 判断权限。
- 后续即使 `agent-admin` 使用独立域名，也由 `agent-admin-api` 统一承接登录入口和业务 API。

优点：

- 性能好。
- 不需要每次请求回调 `sub2api`。
- 适合部署在同一服务器、共享配置的场景。
- 前端只需要对接 `agent-admin-api` 一个 API base，独立域名部署更清晰。

风险：

- JWT secret、issuer、audience、过期策略、token version 等规则需要与 `sub2api` 保持同步。

### 应急方案：调用 sub2api 校验登录态

- `agent-admin-api` 收到 JWT 后调用 `sub2api` 当前用户接口校验。
- 可加短期缓存降低请求量。

优点：

- 不需要共享 JWT secret。

缺点：

- agent-admin-api 运行时依赖 sub2api API 可用性。
- 性能和故障边界较差。

## 5. 用户角色

### 基础管理员

基础管理员来自原 `sub2api` 用户表中的管理员角色。基础管理员可以：

- 登录 `agent-admin` 管理端。
- 授权或撤销其他原系统用户成为 `agent-admin` 管理员。
- 管理 Agent Admin 系统设置。
- 指定原系统用户为代理商。
- 设置代理等级。
- 设置 2 级、3 级代理的上级代理。
- 设置代理商分成比例。
- 手动调整客户归属代理。
- 完整调整代理业务配置，用于处理代理商异常、历史配置错误和运营纠纷。
- 调整代理等级、上级代理、分成比例、客户归属、生效时间、结算状态和必要账务修正。
- 查看全局代理业务数据。
- 管理结算记录。
- 查看审计日志。

### Agent Admin 授权管理员

授权管理员由基础管理员在 `agent-admin` 中指定，账号仍使用原系统账号密码。授权管理员可以：

- 登录 `agent-admin` 管理端。
- 管理代理商、客户归属、分成、结算和审计查看。
- 处理代理商异常、历史配置错误和运营纠纷。

授权管理员限制：

- 不能继续授权或撤销其他管理员。
- 不改变原 `sub2api` 用户角色。
- 授权状态只在 `agent-admin` 自有表中维护。

### 代理商

代理商是原系统用户账号上的业务身份。代理商可以：

- 登录 `agent-admin` 代理端。
- 查看自己直接归属客户。
- 查看自己可发展用户，包括自然推荐用户和管理员归属用户。
- 查看客户套餐周期和佣金记录。
- 查看结算记录。
- 查看自己的上级代理账号。
- 查看下级代理汇总数据和分成贡献。
- 把直接归属于自己的可发展用户指定为下级代理商。
- 在权限范围内设置下级代理分成比例。

### 普通用户

普通用户是未被指定为代理商的原系统用户。普通用户可以：

- 被代理通过推荐码引入。
- 被管理员手动归属到某个代理名下。
- 被符合条件的上级代理或管理员指定为代理商。

普通用户成为代理商后，不回溯过去作为普通客户产生的消费分成。

## 6. 代理层级规则

代理支持 3 级：

- 1 级代理：管理员直接指定，无需上级代理。
- 2 级代理：必须指定 1 级代理作为上级。
- 3 级代理：必须指定 2 级代理作为上级。

约束：

- 一个用户同一时间只能有一个代理身份。
- 1 级代理只能由管理员创建。
- 2 级代理可由管理员创建，也可由 1 级代理从自己的可发展用户中指定。
- 3 级代理可由管理员创建，也可由 2 级代理从自己的可发展用户中指定。
- 3 级代理不能继续发展下级代理。
- 代理商只能把直接归属于自己的可发展用户指定为自己的下级代理商，可发展用户包括自然推荐用户和管理员归属用户。
- 管理员不受推荐码来源限制。

## 7. 客户归属与推荐关系

客户归属来源：

- 自然推荐：读取原 `sub2api` 推荐关系。
- 管理员手动归属：写入 `agent-admin` 自有客户归属表。

归属规则：

- 一个客户同一时间只能归属一个代理。
- 自然推荐关系继续由 `sub2api` 原推荐系统维护。
- `agent-admin` 可以读取原推荐关系作为客户归属和下级代理创建依据。
- `agent-admin-api` 定时读取 `user_affiliates`，将代理推荐码引入且尚无 active 归属的用户同步为 `agent_customer_relations.source = referral`。
- 管理员手动归属只写入 `agent-admin` 自有表。
- 管理员手动归属不默认出现在原 `sub2api` 推荐模块中。
- 管理员手动归属客户仅影响未来套餐周期。
- 周期中调整归属，默认从下一个完整套餐周期生效。
- 不允许代理之间自行转移客户归属。
- 管理员调整客户归属必须填写原因并记录审计日志。

重要限制：

由于目标是不修改 `sub2api` 项目，管理员手动归属后的客户不能自动出现在原系统推荐页面中。若后续必须在原系统也展示，需要另行确认是否允许写入原推荐表兼容记录，或允许 `sub2api` 读取 agent-admin 表。

当前实现约束：

- 自然推荐同步只补充尚无 active 代理归属的客户。
- 管理员手动归属优先级高于自然推荐同步。
- 手动归属会先写入 `scheduled` 关系，并按客户当前未结束订阅的最早 `expires_at` 作为下一完整周期生效时间；无未结束订阅时立即生效。
- 调度任务会把到期的 `scheduled` 关系切换为 `active`，并过期该客户旧的 active 关系。

## 8. 分成与结算规则

### 分成比例

默认比例：

- 1 级代理：20%。
- 2 级代理：15%。
- 3 级代理：10%。

调整规则：

- 管理员可以调整 1 级代理比例。
- 管理员也可以调整任意级代理比例，用于纠错和运营处理。
- 1 级代理可以调整直属 2 级代理比例。
- 2 级代理可以调整直属 3 级代理比例。
- 下级比例必须低于上级给该下级的比例。
- 上级比例下调导致已有下级比例不合法时，阻止保存并提示先调整下级比例。
- 比例允许 0%。
- 比例精度到两位小数。
- 默认从下一套餐周期生效。
- 管理员可以指定未来生效时间。
- 历史分成按当时生效比例计算。

### 差额分成

多级代理采用差额分成：

- 下级代理拿自己的比例。
- 上级代理拿自己比例与直接下级比例之间的差额。
- 整条链路总分成不超过最高上级代理比例。

示例：

- 客户周期确认收入为 1000。
- 1 级代理比例 20%。
- 2 级代理比例 15%。
- 3 级代理比例 10%。
- 客户归属 3 级代理：3 级拿 100，2 级拿 50，1 级拿 50。
- 客户归属 2 级代理：2 级拿 150，1 级拿 50。
- 客户归属 1 级代理：1 级拿 200。

### 分成来源

已确认：

- 分成来自客户套餐周期确认收入，不按充值即时结算。
- 分成按套餐周期到期触发统计。
- 周期确认收入以套餐周期结束时的订单实付金额为准。
- 每日定时任务扫描已到期套餐周期后生成佣金。
- 只有周期结束时已经确认、未退款的收入进入分成。
- 结算前退款扣减本周期收入。
- 结算后退款生成负数冲正，在后续结算中抵扣。
- 负数冲正来源包括结算后退款、订单撤销、支付争议、管理员账务调整。
- 金额以最小货币单位存储，例如分。
- 展示金额保留两位小数。
- 尾差归平台。

当前 P0 实现：

- `agent-admin-api` 启动后和每日定时执行佣金生成。
- 只处理 `payment_orders.order_type = subscription` 且状态为 `COMPLETED` 的套餐订单。
- 周期收入按 `(pay_amount - refund_amount) * 100` 转为分；负数按 0 处理。
- 原 `user_subscriptions` 是当前订阅状态表，续费会更新同一行，不适合作为订单周期历史。
- P0 使用 `payment_orders.completed_at` 作为订单周期开始时间，使用 `payment_orders.subscription_days` 推导订单周期结束时间。
- 使用 `agent_customer_relations.effective_at <= period_start_at` 的归属作为周期归属。
- 按代理链路和当期比例生成差额分成，并通过唯一索引保证同一订单同一代理不会重复生成。
- 结算后退款和支付争议形成负数冲正的自动写入入口仍需后续增强；管理员可通过结算调整入口手动处理。

### 结算参数

- 最低结算金额：100 元。
- 分成冻结期：5 天。
- 结算周期：自然月，到月底结算。
- 负数冲正允许结转抵扣后续分成。

结算状态：

- `pending`：待结算。
- `frozen`：冻结中。
- `payable`：可结算。
- `paid`：已结算。
- `reversed`：已冲正。

线下结算登记：

- 当前不做线上打款，只支持管理员在线下完成付款后在系统登记。
- 只有 `payable` 状态的结算记录可以登记付款。
- 登记时金额必填，支付方式、支付时间、流水号和备注均可选。
- 支付方式可选：银行转账、支付宝、微信支付、现金、其他。
- 登记后结算状态变为 `paid`，记录付款金额、登记时间、登记人和可选备注。
- 代理商可以在自己的结算记录中查看管理员登记的付款信息。
- 首期只支持一条结算一次登记，不做拆分付款；登记错误时由管理员通过结算调整能力处理并进入审计日志。

P0/P1 先做系统生成结算记录和管理员线下结算登记，代理主动提现申请后置。

- 我的工作台。

- 下级代理客户明细。

## 10. 代理禁用规则

- 禁用代理身份后，该用户不能以代理身份登录 `agent-admin`。
- 禁用后该代理不再产生新的分成。
- 历史客户归属、佣金、结算和审计记录保留。
- 被禁用代理名下客户后续归属由管理员手动调整。
- 未调整前显示为“无有效代理分成”状态。
- 下级代理身份继续有效。
- 被禁用代理原本应获得的差额分成归平台。
- 管理员可以恢复代理身份，恢复后从后续套餐周期开始重新产生分成。

## 11. 权限边界

基础原则：

- 权限隔离必须在 `agent-admin-api` 后端强制实现。
- 前端隐藏不作为权限边界。
- 所有写操作都需要审计。
- 管理员具备代理业务的最高调整权限，可处理代理商无法自行解决的问题。
- 管理员的强制调整仍必须记录操作人、原因、调整前后数据和生效时间。

管理员：

- 可查看和管理所有代理数据。
- 可强制调整代理层级、上级代理、比例、客户归属、结算记录和账务修正。
- 可覆盖代理商权限限制，但不能绕过审计。

代理商：

- 只能访问自己直接归属客户。
- 可查看上级代理账号字段：用户名、邮箱、代理等级、联系信息。
- 可查看下级代理的自然月汇总和分成贡献。
- 不能查看下级代理客户明细。
- 不能访问其他代理数据。
- 不能访问 `sub2api` 主后台资源。

## 12. 技术架构概览

目标架构：

```text
agent-admin-web
  -> agent-admin-api
      -> shared database
      -> read sub2api users/referral/orders/subscriptions
      -> write agent-admin owned tables

sub2api
  -> shared database
```

部署关系：

- `sub2api` 和 `agent-admin` 部署在同一服务器或同一内网。
- 两者连接同一个数据库。
- 两者可以分别独立发布和回滚。
- `agent-admin` 不依赖修改 `sub2api` 代码。
- `agent-admin` 默认打包为一个容器镜像，镜像内同时运行前端 Nginx 和 `agent-admin-api`。
- 对外只暴露一个 Web 端口，前端和 API 使用同一个域名。

## 13. 数据表边界

`agent-admin` 自有表：

- `agent_profiles`
- `agent_commission_rates`
- `agent_customer_relations`
- `agent_customer_relation_changes`
- `agent_commission_periods`
- `agent_settlements`
- `agent_settlement_payments`
- `agent_admin_users`
- `agent_audit_logs`
- `agent_admin_schema_migrations`

`agent-admin` 可读取的 `sub2api` 表：

- `users`
- `user_affiliates`
- 原订单表。
- 原订阅套餐表。
- 原套餐周期或用量表。
- 原退款或支付审计表。

原则：

- 自有表可写。
- 原系统表默认只读。

## 15. 已确认结论

- `agent-admin` 后续独立更新。
- `sub2api` 后续独立更新。
- 两者部署在同一服务器或同一内网。
- 两者共用数据库。
- `agent-admin` 不修改 `sub2api` 项目。
- 认证相关继续使用 `sub2api`。
- 登录请求由 `agent-admin-api` 代理到 `sub2api` 登录接口。
- `agent-admin-api` 使用本地 JWT 验签。
- JWT secret、签名算法、claims、过期和失效规则与 `sub2api` 保持一致。
- 管理员身份由 `agent-admin-api` 本地验签后读取共享数据库中的原用户角色判断。
- 代理业务 API 和数据库读写由 `agent-admin` 自行完成。
- 管理员和代理商都可以登录 `agent-admin`。
- 管理员和代理商使用与原系统一致的账号密码。
- 一个客户同一时间只能归属一个代理。
- 分成按套餐周期到期触发统计。
- 分成金额按周期确认收入计算。
- 周期确认收入以套餐周期结束时的订单实付金额为准。
- 多级代理采用差额分成。
- 默认比例为 20%、15%、10%。
- 最低结算金额 100 元。
- 冻结期 5 天。
- 结算周期按自然月月底结算。
- 负数冲正可结转抵扣后续分成。
- 当前已经加入 `sub2api` 后端的 agent-admin 代码需要从 `sub2api` 删除，后续迁移到独立 `agent-admin-api` 时仅作为参考。
